# Release Blocker 01 — Remediation

Date: 2026-11-16 · Companion to `RELEASE-BLOCKER-01-DEPENDENCY-AUDIT.md` (findings) and `RELEASE-BLOCKER-01-TEST-REPORT.md` (evidence).

**Verdict: RESOLVED.** Every critical and high advisory is fixed. That covers the Phase 8 set (Next.js, zod, body-parser, multer, xlsx) plus tinypool and vite, which became detectable after Phase 8. `pnpm audit` reports 0 critical / 0 high. The regression suites pass, except for documented environment limitations and three pre-existing defects that this change did not introduce: the WebKit login hydration race, the COD label association, and an intermittent realtime presence test. This verdict covers dependency remediation only. It is **not** a production-readiness claim; the other Phase 8 blockers remain open (`PHASE-8-FINAL-REPORT.md`).

## 2. Decisions and justification

### 2.1 zod 3 → 4 (the only major upgrade that was unavoidable)

The fix exists only in zod 4.6.6+ and only in the v4 implementation (commit `a0ebf970`, PR colinhacks/zod#6652: size bounds are checked before elements are parsed). Importing `zod/v3` from the zod 4 package would have silenced the audit **without** removing the vulnerability, so the code was migrated to the zod 4 API instead.

Behaviour-preserving migration (contracts are the shared API boundary):

| zod 3 construct                                    | Where                                         | zod 4 replacement                                                              | Why                                                                                                                                                                                |
| -------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `z.string().uuid()` (61 uses)                      | all contract modules                          | `z.string().guid()`                                                            | zod 4 `uuid()` accepts only RFC 9562 ids; seeded/fixture ids such as `a0000000-…-000000000001` would be rejected. `guid()` uses the same 8-4-4-4-12 hex pattern as zod 3 `uuid()`. |
| `{ required_error: "…" }`                          | `parcelBookingSchema` (5 fields)              | `{ error: requiredMessage("…") }` — message only when `input === undefined`    | Same semantics as zod 3; other type errors keep the default message.                                                                                                               |
| `{ invalid_type_error: "…" }`                      | parcel `codAmount`, `weight`; payout `amount` | `{ error: "…" }`                                                               | In zod 4 the schema-level `error` covers only that schema's type issue, like zod 3.                                                                                                |
| `z.coerce.number()` input type                     | parcel `codAmount`, `weight`                  | `z.coerce.number<number \| string>()` + exported `ParcelBookingInput`          | zod 4 types coerced input as `unknown`; declaring it keeps the web form strictly typed without casts. Runtime unchanged.                                                           |
| `z.record(V)`                                      | 3 schemas                                     | `z.record(z.string(), V)`                                                      | zod 4 requires the key schema.                                                                                                                                                     |
| `ZodType<O, ZodTypeDef, I>`                        | `ZodValidationPipe`, `ChatGateway.admit`      | `ZodType<O, I>`                                                                | Generic signature changed.                                                                                                                                                         |
| `class RequestOtpDto implements IRequestOtpDto {}` | `riders/dto/rider-delivery.dto.ts`            | `class RequestOtpDto {}` (comment explains)                                    | zod 4 infers a strict empty object as `Record<string, never>`, which a class cannot implement. Empty body either way.                                                              |
| `useForm<ParcelBooking>`                           | web booking form + 4 section components       | `useForm<ParcelBookingInput, unknown, ParcelBooking>` / `ParcelBookingControl` | @hookform/resolvers 5 separates form input from validated output.                                                                                                                  |

Regression tests added: `packages/contracts/src/zod4-compat.test.ts` (5) — non-RFC ids still accepted, required-field vs wrong-type messages, custom number message, record validation, and the advisory itself (200 000-element array against `.max(500)` yields < 5 issues; zod 3.25.76 produced one issue per element).

### 2.2 xlsx from the vendor CDN

SheetJS stopped publishing to npm at 0.18.5; fixed releases (0.19.3+, 0.20.2+) are distributed only from `cdn.sheetjs.com`, which is SheetJS's documented installation method. 0.20.3 is the newest release there. The tarball URL is recorded in the lockfile with a sha512 integrity hash, so installs are reproducible and tamper-evident. The API's write-only use (`aoa_to_sheet`, `book_new`, `book_append_sheet`, `write`) is unchanged; a round-trip check (headers, Bengali text, numbers, nulls, CSV-sensitive characters) is identical.

Trade-off: a non-registry dependency is not covered by `minimumReleaseAge` and future advisories for it will not show in `pnpm audit` by version range. Owners should watch SheetJS releases manually. Alternative considered: replacing SheetJS with another writer (new dependency, larger change) — rejected for this blocker.

### 2.3 tinypool override (dev tooling)

vitest 3.2.7 (latest 3.x) depends on `tinypool ^1.1.1`; no 1.x fix exists. tinypool 2.0's only breaking change is dropping Node 18 (repository engines: Node ≥ 20.18; runtime Node 26). The override is scoped (`vitest>tinypool`) and documented in `pnpm-workspace.yaml` with its removal condition. Verified by running every vitest suite in the repo with tinypool 2.2.0 (unit, component, contracts, integration). Alternative — vitest 3 → 5 (two majors in three workspaces) — rejected as unnecessary for this blocker.

## 4. Rollback

Revert the manifest/lockfile/workspace changes and the zod migration together (they are coupled: zod 4 code does not compile against zod 3). Backups of the pre-change manifests and lockfile were kept outside the repository during the work; `git` history is the authoritative rollback path once committed. No database, migration or infrastructure change is involved.
