# Communication Platform — Phase 6 Security Review

## 1. Controls

| Threat                                          | Control                                                                                                                                                                                | Evidence                                                                                                                                                                   |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unauthorized upload                             | Reserve requires ACTIVE + live-eligible participant with `SEND_MESSAGE` in a writable conversation (same gate as sending)                                                              | Integration: other tenant, ineligible rider, admin without intervention → 404                                                                                              |
| Trusting client MIME / size / extension / name  | Declaration checked against the shared policy; after upload the server streams the stored object: exact size, SHA-256 and magic bytes must match the declared type                     | Unit: signatures for every type, HTML/SVG/EXE masquerading rejected; integration: signature, checksum and size mismatches → REJECTED + object deleted + audit              |
| Client-chosen object keys / path traversal      | Keys are `chat/<conversationId>/<attachmentId>` generated server-side; filenames never reach storage paths; filename schema forbids `/`, `\`, control chars                            | Unit + integration (`../../x.png` → 422; key assertion)                                                                                                                    |
| Public bucket / credential exposure             | Private bucket; only short-lived single-key presigned URLs (PUT 5 min, GET 5 min) are issued; credentials stay server-side (or SDK role); responses and realtime carry no keys or URLs | Integration: history contains no `chat/` key or signature; E2E log audit: 0 signatures/credentials/tokens                                                                  |
| Cross-tenant / cross-conversation access        | Download re-checks live membership of the attachment's conversation; send requires same conversation + same uploader + unused                                                          | Integration: other tenant/ineligible/admin → 404; foreign, reused, cross-conversation, wrong-type attachments → 422; E2E: newly registered merchant → 404, anonymous → 401 |
| Pending / rejected / deleted content            | Download only for `UPLOADED`; deleted message ⇒ 404 even for the sender; unsent ⇒ uploader only                                                                                        | Integration                                                                                                                                                                |
| Reuse of another user's attachment              | Complete/cancel uploader-only (404 for others); send enforces uploader                                                                                                                 | Integration                                                                                                                                                                |
| Content sniffing / script execution on download | Served `Content-Type` is the verified type; PDFs `attachment`; `nosniff`-style risk limited because only raster images, PDF and audio are allowed (no SVG/HTML)                        | Policy + signature tests                                                                                                                                                   |
| Upload abuse                                    | Rate limits (`chat-upload` 30/min, `chat-download` 240/min); per-type size caps; ≤20 unfinished uploads per user; server reads stop past the type limit                                | Integration (pending limit)                                                                                                                                                |
| Storage errors leaking internals                | Provider errors → 503 `CHAT_STORAGE_UNAVAILABLE`, logged by operation and error name only                                                                                              | Code review                                                                                                                                                                |
| Deleting referenced objects                     | Cleanup/cancel claim rows with `message_id IS NULL` (committed) before deleting objects; linked rows never touched                                                                     | Integration cleanup test (linked attachment survives and stays downloadable)                                                                                               |
| Audit                                           | `ATTACHMENT_REJECTED` with reason, DB-loaded actor role; download denials and storage errors logged (no URLs)                                                                          | Integration                                                                                                                                                                |

## 2. Not provided (documented limitations)

- **Malware scanning:** no scanner exists in the infrastructure and adding one is out of scope. `UPLOADED` means type/size/integrity-verified, not malware-free. The UI never labels files as safe. PDFs are downloaded (not rendered inline by the app). Recommended before production: an asynchronous scan step (e.g. ClamAV worker on the existing BullMQ queue) gating `UPLOADED`.
- **Deep content validation:** signatures prove the container type, not that the whole file is well-formed (e.g. a JPEG header followed by arbitrary bytes passes). Browsers decode images in sandboxed decoders; no server-side image re-encoding (no image library in the stack).
- **No server-side thumbnails** (originals are displayed scaled, lazily loaded).
- **Staff non-participant access** to attachments (Phase 7 admin centre) is not implemented; staff must intervene first.
- Presigned GET URLs are bearer URLs for their 5-minute lifetime if copied out of the browser.
- Attachments of deleted messages are retained indefinitely for moderation until a Phase 7 retention policy.
